# Agents and orchestration (🤖 / 🔁 / 🏁)

With "Agent" when you create a task, you choose whether it runs on **Claude Code / Codex CLI / Antigravity CLI / Gemini CLI / Cursor CLI / OpenCode / Copilot CLI / Amp / Pi / Droid** (only the agents checked under "Agents to use" in Settings are offered). You can also choose **orchestration**, which combines several agents.

| Choice | What happens |
| --- | --- |
| Claude Code / Codex CLI / Antigravity CLI / Gemini CLI / Cursor CLI / OpenCode / Copilot CLI / Amp / Pi / Droid | The task runs as one card on that agent (worktree, commits, merge, and PR work as usual) |
| 🔁 Pipeline | Agents hand the work over step by step, following the **flowchart** in Settings (for example: implement with Codex → review with Claude → back to implementation if changes are needed). Steps run in the same worktree (only parallel branches use separate worktrees). Changes are committed after each step, and the final report is passed to the next step. If a step fails or stops on a question, the Pipeline stops there (fix it with a follow-up instruction and it moves on to the next steps). When all steps are done, the task moves to the Review column. You can follow progress on the card's bar and in the workflow view in the detail panel (each step's state, agent, time taken, cost, and the report passed on) |
| 🏁 Competition | The agents of the chosen competition solve the same task **in parallel**, each on its own card (separate worktrees and branches). You get a notification when all of them finish. Compare the candidates in the "🏁 Competition" area of the "Progress" tab in the detail panel. Use "🤔 Ask ○○ to compare" to start a conversation comparing them (it asks the agent selected by default), or "🏁 Adopt this proposal" to discard the other candidates. Bring in the adopted proposal with a merge or a PR as usual |

- Under "Agents to use" in Settings, check the agents you want (at least one). Only checked agents can have a command path and model set, and only they can be chosen for tasks, conversations, Pipeline steps, and competition (the first launch checks every agent that is installed; if none is found it checks Claude Code only and looks again at the next launch; after an upgrade from an earlier version, the agents you were using are checked)
- The "Agent" field when you create a task lists single agents, custom agents, Pipelines, and competitions together, and you pick one of them
- What is selected by default for new tasks and conversations is chosen per project, from the agents to use, this project's custom agents, Pipelines, and competitions ("Selected by default for new tasks and chats" under "Agents" in Settings). When a Pipeline or competition is chosen, conversations, and tasks where it cannot be used (for example because a step's agent is unchecked), use the first of the agents to use. Competition comparison and flowchart building use the base agent of a custom agent, or the first of the agents to use for a Pipeline or competition
- Under "Orchestration" in Settings, you can create any number of **Pipelines** (built in the screen opened with "Edit flowchart") and **competitions** (each with two or more agents that solve the same task) per project
- **Multiple competitions**: use "+ Add competition" to add one, then give it a name and choose the agents and custom agents that compete ("Duplicate" and "Delete" are there too). Changes to the competition list are saved with "Save" in Settings. The "agents to compete" from earlier versions become the first competition, named "Competition"
- **Multiple Pipelines**: use "+ Add a Pipeline" to add one with a name. Each Pipeline has "Edit flowchart", "Name", "Duplicate", and "Delete" (the last one cannot be deleted). The "Agent" field shows all Pipelines when you create a task. A task you have created keeps running on the flow it had when it was created, even if you later change or delete the Pipeline
- **Export**: "Export" on a Pipeline writes that Pipeline alone to a `.json` file. "Export together (zip)" (and "zip" on each Pipeline) lets you pick Pipelines and custom agents and writes them to one zip (custom agents used in the steps of the chosen Pipelines start out checked)
- **Import**: with "Import (.json / .zip)", choose a Pipeline `.json` file or a combined zip. After you confirm what will be imported, it is added to the current list (a duplicate name becomes "Name (2)"). A custom agent with identical contents is reused; otherwise it is added, and the step's agent is pointed at it. If you import a `.json` without custom agents and a step's custom agent cannot be found, choose one again in the flowchart
- **Editing the flowchart**: add nodes with "+ Step", "+ Branch (if)", "+ Parallel", "+ Join", and "+ End", and arrange them by dragging. Dragging where there is no node or line scrolls the canvas. Drag from the circle at the bottom of a node (its exit) to another node to connect them. Select a node or line to change its contents in the right-hand panel (a step's agent, name, and role description; a branch's expected values and conditions; a loop's limit), and delete it with the Delete key. If you choose a custom agent for a step and the step's name is empty, the custom agent's name is filled in (the same happens if you save it empty). Zoom with the "−", "+", and "Fit" buttons at the top right, by scrolling while holding ⌘ (Ctrl on Windows and Linux), or by pinching on a trackpad (press the zoom percentage to return to 100%). While something needs fixing, a list appears at the bottom and you cannot save. "Save" immediately saves to this project's settings (step lists from earlier versions have been moved into the flowchart)
- **Branch (if)**: place it right after a step. The step's agent is asked to end its reply with `[[RESULT:value]]`, and the route is chosen by comparing that value with the **expected value** set on each line leaving the branch (for example `ok` / `bug` / `docs`; case does not matter). There can be three or more lines. A line's **explanation** tells the agent when to write that value. If no expected value matches (or nothing was written), the line set as "when nothing matches" is followed. If there is no such line, the Pipeline stops and tells you (have the agent rewrite it with a follow-up instruction and it continues)
- **Creating or changing a flowchart from text**: describe the flow you want or what to change in the box at the top of the editor, then press "Apply with AI" (⌘ + Enter, or Ctrl + Enter on Windows and Linux). The agent builds the flow and shows it on the screen (for example: "Implement with Codex, review with Claude, and go back to implementation if anything needs fixing", or "Add a test step before the review step"). The flow is built by the agent selected by default (if that agent is unchecked, the first of the agents to use). Only agents to use and custom agents are chosen for steps. When nodes or lines change, the layout is rearranged automatically. Settings do not change until you press "Save". "Undo" returns to the state before the change. Anything that could not be corrected appears under "Issues to fix" at the bottom
- **Loop**: drawing a line back to an earlier node makes a loop (shown as a dotted line). Each line has a "Loop limit" (default 3, from 1 to 10). When the limit is reached, the Pipeline finishes, moves the task to the Review column, and tells you
- **Parallel → Join**: draw two or more lines out of a Parallel node and connect the end of each branch to the same Join. Each branch runs at the same time as a "parallel-branch task" (with its own card on the board) in a separate worktree split from this task's branch. When all branches reach the Join, their changes are merged into this task's branch in turn, the parallel-branch tasks are cleaned up, and the flow moves on. If any branch fails or stops on a question, the original task keeps waiting (fix or answer it on the parallel-branch task and it continues). If a merge conflicts, it stops and tells you. Resolve it from the "Conflict" area at the end of the "Chat" tab in the detail panel, and the remaining branches are merged and the next step starts. You cannot put another Parallel inside a branch. In a folder not managed by git, branches cannot get their own working copies, so the parallel-branch tasks run one at a time in the same folder, and when all of them finish the flow moves past the Join without merging
- In the workflow view in the detail panel, you can see each step's state, run count, judged value, loop count, skipped steps, and the state of parallel branches
- When a task is stopped in review or has failed, you can return to the point just before a step or a run. Files, Pipeline progress, and the conversation go back to that point, later changes are discarded, and work starts right away. See [Restore an earlier point](usage.md#restore-an-earlier-point)
- Branch naming, conflict resolution, the spec check, conversations, and skill suggestions work on every agent (branch names and conflict resolution are handled by the task's agent)
- Tasks created from an Issue can also choose an agent, Pipeline, or competition (with competition, each Issue gets one card per agent)
- Codex runs as `codex exec --json` (`codex app-server` when you approve on the card), Antigravity as `agy --output-format stream-json`, Gemini as `gemini --output-format stream-json`, Cursor as `cursor-agent acp` (`cursor-agent -p --output-format stream-json` on versions without it), OpenCode as `opencode run --format json`, Copilot CLI as `copilot -p … --output-format json`, Amp as `amp -x --stream-json` (`amp threads continue` to continue), Pi as `pi --mode json`, and Droid as `droid exec -o stream-json`. Follow-up instructions continue the same conversation
- Because of how their CLIs work, Codex / Antigravity / Gemini / Cursor / OpenCode / Copilot / Amp / Pi / Droid do not support multiple-choice questions, btw (messages while running), continuing an existing conversation (from the terminal), or cost display
- **In-card approval** works on Claude Code, Codex, and Cursor. "Always allow" is remembered only for that card. The allowed tools setting also applies (a prefix rule such as `Bash(npm test:*)` does not match commands chained with `;` or `|`). Each permission mode works as follows

| Permission mode | Codex | Cursor | Antigravity | Gemini |
| --- | --- | --- | --- | --- |
| Plan only | Read-only sandbox | Plan mode | `--mode plan` | `plan` |
| Auto-approve file edits (`acceptEdits`) | Edits inside the worktree and commands inside the sandbox just run; anything leaving the sandbox (network, writes outside the worktree, and so on) is **approved on the card** | File edits just run; commands not in allow in Cursor's `cli-config.json` are **approved on the card** | File edits inside the worktree are allowed automatically (`--mode accept-edits`) | File edits are allowed automatically (`auto_edit`) |
| Ask every time (`default`) | Commands and file changes are **approved on the card** | Commands not in allow are **approved on the card** (Cursor does not ask about file edits, so they are written directly) | Changes are denied (`default`) | `default` |
| Allow everything automatically | `--dangerously-bypass-approvals-and-sandbox` | `--force --approve-mcps` | `--dangerously-skip-permissions` | `yolo` |

OpenCode, Copilot CLI, Amp, Pi, and Droid do not support in-card approval, so the CLI allows actions according to the permission mode. Anything that needs confirmation is refused on the spot, because the CLI cannot ask in headless mode (it does not wait). OpenCode, Amp, and Pi run commands without asking by default, so commands are turned off in every mode except "Allow everything automatically" (tasks created from Issues or Slack never run with "Allow everything automatically", so instructions written by outsiders cannot run commands either)

| Permission mode | OpenCode | Copilot CLI | Amp | Pi | Droid |
| --- | --- | --- | --- | --- | --- |
| Plan only | `--agent plan` (refuses file changes); commands need confirmation (so they are refused) | `--plan` | File-changing tools and commands (`edit_file` / `create_file` / `undo_edit` / `Bash`) are turned off | Read-only tools only (`--tools read,grep,find,ls`) | No flag (read-only) |
| Auto-approve file edits (`acceptEdits`) | Commands need confirmation (so they are refused) | Only file writes are allowed (`--allow-tool=write`) | Commands (`Bash`) are turned off | No commands (`--tools read,edit,write,grep,find,ls`) | `--auto low` (up to file edits) |
| Ask every time (`default`) | File edits, commands, and web fetches need confirmation (so they are refused) | Nothing is allowed | Commands (`Bash`) are turned off | No commands | No flag (read-only) |
| Allow everything automatically | `--auto` | `--allow-all` | `--dangerously-allow-all` | No limits | `--skip-permissions-unsafe` |

- OpenCode's permissions are passed in `permission` of the `OPENCODE_CONFIG_CONTENT` environment variable (read on top of your usual `opencode.json`). For Amp, a copy of your usual settings (`~/.config/amp/settings.json`) with `amp.tools.disable` added is passed with `--settings-file`
- To let them run commands such as tests, choose "Allow everything automatically". When Droid tries something it is not allowed to do (for example a command under "Auto-approve file edits"), the run ends on the spot and the card shows an error (edits made so far stay)
- Copilot CLI receives the instruction as the `-p` argument. It runs with `--no-ask-user` because it cannot ask back in headless mode. The attachments folder is made readable with `--add-dir`
- Amp needs the `AMP_API_KEY` environment variable (`sgamp_…`) to run headless (an `amp login` session does not work). Amp has no model choice, so the "Model" in Settings or on a task is passed to `--mode` (`low` / `medium` / `high` / `ultra`, and so on)
- Droid needs `FACTORY_API_KEY` to run headless
- Pi exits with code 0 even when a reply fails, so the `stopReason` in its output is used to detect errors. Pi does not report TODOs, so the TODO list in the Progress tab stays empty (the same goes for Copilot CLI, whose output does not include the TODO contents)
- OpenCode decides its working folder from `PWD`, so it is started with the worktree path in `PWD` as well
- The Codex app-server protocol changes between versions, so availability is checked just before running. The same goes for Cursor. On versions where it does not work, the previous behavior is used (a `workspace-write` sandbox on Codex, `--force` on Cursor), and the log says so. Verified versions are Codex 0.150.0 and 0.167.0, and Cursor 2026.11.05
- Cursor stores `acp` and `-p` conversations separately, so a card started with `-p` by an earlier version keeps using `-p` (no in-card approval). Conversations started from now on can be approved on the card
- Antigravity denies commands that are not allowed on the spot, because it cannot ask in headless mode. To let it run commands such as tests, list them under `permissions.allow` in `~/.gemini/antigravity-cli/settings.json` (for example `"command(npm test)"`), or choose "Allow everything automatically"
- For Antigravity, start `agy` once in a terminal and sign in first. Without that, the card shows an authentication error
- Gemini CLI stopped working for Google AI Pro / Ultra and free personal accounts on June 18, 2026 ([Google's announcement](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)). It still works with paid API keys and Gemini Code Assist Standard / Enterprise. On a personal account, choose Antigravity CLI
- When you choose a skill, Claude Code receives it as `/skill-name`, and other agents are told where its SKILL.md is and follow those steps
